# Phase 2 approved implementation decisions

Authority: the user explicitly requested implementation of the Phase 2 plan after choosing SQLAlchemy/SQLite, unapplied IaC, mixed metadata ownership, Registry REST validation, terminal resolution and minimal private networking. No deployment or Phase 3 is authorized.

- **Local persistence:** separate SQLite files and SQLAlchemy metadata per service. SQLite foreign keys are enabled. Registry owns intersections/sensors; Incident Manager owns incidents, with no cross-database SQL or cross-service foreign key.
- **Planned PostgreSQL:** one RDS database `smarttraffic`, separate `sensor_registry` and `incident_manager` schemas, separate NOLOGIN owner roles and IAM-authenticated LOGIN application roles. Initial bootstrap and table DDL are prepared, not PostgreSQL-tested. Migrations use owner roles; runtime roles have only schema usage and select/insert/update on their own tables. Later membership/identity policy and TLS connectivity must be verified before deployment.
- **Metadata:** clients choose domain IDs. Server-generated incident UUID event IDs and UTC timestamps describe the current record revision, not a published event. Create starts open; unchanged patches preserve event ID/timestamps; material patches replace event ID/updated timestamp. Resolution is terminal; no outbox, queue publication or alert exists.
- **REST:** interfaces and error responses are documented in [phase-2-api.md](../phase-2-api.md). Sensor/intersection IDs and sensor intersection assignment are immutable. Incident ID/intersection/type/reported timestamp are immutable. Blank inputs, extra fields, empty or null patches are rejected. Incident creation validates an intersection using one Registry GET, two-second HTTPX timeouts, no retries, no environment proxies and no redirects.
- **Consistency:** incident updates use SQLAlchemy's version column to reject conflicting writes with 409. Unique IDs and Registry foreign keys are enforced in SQL. Registry reference validation is not a cross-service transaction, but intersection deletion is not supported. Failed Registry validation precedes incident insertion.
- **Local scope:** preserve the original health payload; it is liveness only. Enable docs on the two implemented APIs. All other six service entry points retain their Phase 1 behavior. API security is local loopback only here; public authentication is later work.
- **Unapplied IaC:** AWS provider 6.45.0; Mumbai VPC, two isolated subnets, application/database security groups, PostgreSQL 17, db.t4g.micro, 20 GiB gp3, single AZ, encrypted storage, required TLS, IAM DB authentication and RDS-managed master credentials. No Internet/NAT gateways. Database ingress is only TCP 5432 from the application group. This group has no public ingress and only database egress; later application networking must be designed in its deployment phase.
- **Deployment controls:** approval defaults false and blocks successful resource planning through a lifecycle precondition. Tests use `mock_provider` and plan-only runs. No real AWS plan or apply is authorized. Deletion protection, one-day automated backups and a final snapshot are enabled; teardown/backup retention must be explicitly reviewed against the US$10 cap and US$0.50 reserve before any future deployment. Do not silently disable protections or assume a 20-minute demo bounds all charges.
- **Deferred:** AWS costs/access/quotas remain user-accepted planning assumptions; actual region/instance/engine availability, protected remote Terraform state, RDS service-linked-role/IAM prerequisites, workload credentials, Linux packages and live PostgreSQL behavior are unverified. No resource was provisioned.
